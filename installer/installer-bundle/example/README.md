# Example installer bundle

This directory is a small, OSS-safe bundle staging example. It documents the
shape accepted by the installer; it is not a complete product release bundle.

The installer consumes a gzip-compressed tar archive, not a Go module or a
generic OCI artifact. Build an archive with this directory as its root so the
archive contains:

```text
checksum.json       # generated by the bundle build step
deployments/
images/
manifests/
  images.yaml
  models.yaml
```

`checksum.json` is deliberately absent from source control. It must be
generated after all payload files have been copied into the staging directory.

## Build and run the example

From the repository root:

```bash
./installer/installer-bundle/scripts/build-bundle.sh \
  installer/installer-bundle/example \
  installer/installer-bundle/example.tar.gz

./installer/installer-bundle/scripts/deployment.sh \
  --bundle installer/installer-bundle/example.tar.gz
```

The deployment helper builds `installer:latest` by default, uses
`$HOME/.kube/config`, and stores persistent installer state in
`./shaide-installer-data`. Use `--no-build` after the image is available.

## What belongs here

- `deployments/` contains canonical Pulumi project metadata, local Helm charts,
  CRDs, and model-serving values referenced by the installer. Stack-specific
  `Pulumi.<stack>.yaml` files are intentionally omitted; the installer creates
  them when it initializes each stack.
- `images/` contains OCI image archives only for `source: archive` entries in
  `manifests/images.yaml`.
- `manifests/images.yaml` inventories images to upload or mirror.
- `manifests/models.yaml` inventories Hugging Face model artifacts. Model files
  are downloaded at install time and are not copied into this directory.

The example inventories the GPT-OSS-20B model and the remote images required by
the corresponding app-shaide, app-serving, and gateway deployments. The image
entries are pulled from their original registries; no local OCI archives are
required for this connected example. A release bundle should update the pinned
versions and model revision when its deployment profile changes.

## Installer project names

The directory names below are part of the installer contract:

| Directory | Project | Project file |
| --- | --- | --- |
| `deployments/cloud-harbor` | `cloud-harbor` | `Pulumi.yaml` |
| `deployments/harbor` | `k8s-onprem-airgap-services` | `Pulumi.yaml` |
| `deployments/gateway-provider` | `gateway-provider` | `Pulumi.yaml` |
| `deployments/app-serving` | `app-serving` | `Pulumi.yaml` |
| `deployments/app-shaide` | `app-shaide` | `Pulumi.yaml` |
| `deployments/monitoring` | `monitoring` | `Pulumi.yaml` |

The example also vendors the assets used by the offline deployment paths:

```text
deployments/cloud-harbor/charts/harbor-1.18.2.tgz
deployments/harbor/charts/harbor-1.18.2.tgz
deployments/monitoring/charts/{loki-14.1.0,grafana-12.3.2,alloy-1.8.1,prometheus-29.21.0}.tgz
deployments/app-serving/charts/inferencepool/
deployments/app-serving/upstream/llm-d/llm-d-infra/charts/llm-d-infra/
deployments/gateway-provider/crds/{gateway-api,gie}/
```

Do not copy generated Pulumi secrets, `encryptionsalt` values, model caches, or
runtime state into an OSS bundle. The installer injects secrets at runtime.
